# 第一章 算力硬件基础

## 1.1 先建立三个数量级概念

学显存计算之前，必须先分清三件事，否则后面公式全是糊的：

| 概念 | 单位 | 通俗理解 | 决定了什么 |
| --- | --- | --- | --- |
| **显存容量**（Memory Capacity） | GB | 桌子有多大 | 模型**能不能跑起来** |
| **显存带宽**（Memory Bandwidth） | GB/s | 手从桌上拿东西有多快 | 推理**吐字快不快**（decode 速度） |
| **算力**（Compute，FLOPS） | TFLOPS | 脑子算得有多快 | 训练**要跑多久**、prefill 快不快 |

**关键认知**：新手总以为"卡不够"是算力不够，实际上 90% 的情况是**显存容量不够**（装不下）或**显存带宽不够**（生成慢）。大模型推理的解码阶段是典型的 **memory-bound（带宽受限）**，不是算力受限——所以 A100 和 H100 跑 7B 模型单条对话的速度差距，远小于它们算力标称值的差距。

## 1.2 常用算力卡详细对比

**1 台标准算力服务器 = 8 张卡**（这是行业惯例配置，面试说"一台 A100 服务器"默认指 8×80G = 640GB 显存）

| 显卡型号 | 显存 | 显存带宽 | FP16 算力 | 卡间互联 | 适用场景 |
| --- | --- | --- | --- | --- | --- |
| **A100 40G** | 40GB HBM2 | 1.55 TB/s | ~312 TFLOPS | NVLink 600GB/s | 中等规模模型训练/推理，7B 全参微调 |
| **A100 80G** | 80GB HBM2e | 2.0 TB/s | ~312 TFLOPS | NVLink 600GB/s | **大规模模型训练主流选择**，32B 推理 / 70B 量化推理 |
| **A800 80G** | 80GB HBM2e | 2.0 TB/s | ~312 TFLOPS | NVLink **降至 400GB/s** | 国内合规版 A100，单卡性能相同，**多机多卡训练略慢** |
| **H100 80G** | 80GB HBM3 | 3.35 TB/s | ~989 TFLOPS(FP16) | NVLink 900GB/s | 千亿模型训练首选，支持 FP8，比 A100 快 2~3 倍 |
| **H800 80G** | 80GB HBM3 | 3.35 TB/s | ~989 TFLOPS | NVLink 降速 | 国内合规版 H100 |
| **L20 / L40S** | 48GB | 0.86 TB/s | ~360 TFLOPS | 无 NVLink（PCIe） | 推理性价比卡，32B 量化部署常用 |
| **RTX 4090** | 24GB GDDR6X | 1.0 TB/s | ~330 TFLOPS | **无 NVLink** | 消费级最强，7B 以下微调/推理；多卡扩展差 |
| **昇腾 910B2** | 32G / 64GB | ~1.6 TB/s | ~376 TFLOPS | HCCS | 国产算力，配 MindSpore / PyTorch+CANN，MindIE 部署 |
| **昇腾 910B3** | 32G / 64GB | ~1.6 TB/s | ~313 TFLOPS | HCCS | 同上，910B 系列不同规格 |

**面试常被追问的点（必须能答）：**

1. **A100 和 A800 的区别？** 单卡算力、显存完全一致，差别只在 **NVLink 互联带宽被限制（600→400 GB/s）**。单卡任务无差别；多卡张量并行、大规模分布式训练时通信成为瓶颈，效率损失约 10%~30%。
2. **4090 为什么不适合训练大模型？** 三个原因：① 显存只有 24GB；② **不支持 NVLink**，多卡只能走 PCIe，通信慢；③ 消费卡驱动协议不允许数据中心部署（合规风险）。
3. **昇腾卡怎么用？** 算子库是 CANN，训练用 MindSpore 或 PyTorch+torch_npu，推理用 **MindIE**（华为官方）或适配版 vLLM。踩坑点：算子覆盖不全，部分模型需手动适配；FP16 精度对齐问题要做回归测试。
4. **显存带宽为什么重要？** 见 1.1，decode 阶段每生成一个 token 都要把**整个模型权重从显存搬到计算单元一次**，所以「单卡生成速度上限 ≈ 显存带宽 ÷ 模型权重大小」。例：A100 80G 跑 14B FP16（28GB 权重），理论上限 ≈ 2000/28 ≈ **71 token/s**，实际约 40~50 token/s。这个估算公式面试很加分。

## 1.3 数据精度：显存计算的基石

**专业定义**：数值精度指单个参数在内存中占用的位宽（bit），决定了表示范围与精度。

**通俗解释**：同一个数字 3.14159，你可以记成 3.14159265（占地方，准）、3.14（省地方，糙）。模型参数就是一堆小数，用几位来记就是精度。

| 精度 | 每参数字节 | 说明 | 典型用途 |
| --- | --- | --- | --- |
| FP32 | 4 Byte | 单精度，最准 | 优化器状态、早期训练 |
| **FP16 / BF16** | **2 Byte** | 半精度，**当前训练与推理主流** | BF16 范围大更稳，A100+ 首选 |
| FP8 | 1 Byte | H100/H20 及新卡支持 | 前沿训练/推理加速 |
| **INT8** | **1 Byte** | 8 位整型量化 | 推理量化，精度损失 <1% |
| **INT4 / NF4** | **0.5 Byte** | 4 位量化 | 极限压缩，损失 1%~3%，QLoRA 用 NF4 |

**记住这一句话，后面所有公式都从它推导：**

> **FP16 下，模型每 1B（10 亿）参数 ≈ 2GB 显存。**
> 换算：INT8 → 1GB/B，INT4 → 0.5GB/B，FP32 → 4GB/B。

严格说 1B 参数 FP16 = 2×10⁹ Byte = 1.86 GiB，工程上直接按 **2GB** 估算，误差 7% 完全够用。

# 第二章 显存到底被谁吃掉了（核心公式）

## 2.1 一张图看懂显存的五个「房客」

**通俗比喻**：把一张 GPU 想象成一间出租房，显存就是房子的面积。里面住着五类房客，谁都要占地方：

```
┌─────────────────────────────────────────────────┐
│  ① 模型权重 Weights      —— 房子的家具，永久占用      │  推理/训练都有
├─────────────────────────────────────────────────┤
│  ② 梯度 Gradients        —— 每个家具的"修改意见"     │  只有训练有
├─────────────────────────────────────────────────┤
│  ③ 优化器状态 Optimizer  —— 修改意见的历史账本（最胖） │  只有训练有
├─────────────────────────────────────────────────┤
│  ④ 激活值 Activations    —— 干活时摊开的临时草稿纸    │  训练很大，推理很小
│     推理时这一项主要表现为 KV Cache                  │
├─────────────────────────────────────────────────┤
│  ⑤ 框架开销 Overhead     —— 水电物业费（CUDA上下文等） │  固定 1~2GB
└─────────────────────────────────────────────────┘
```

**一句话总结两者差异**：
- **推理** = ① 权重 + ④ KV Cache + ⑤ 开销 → 主要看权重
- **训练** = ① + ② + ③ + ④ + ⑤ → 主要看**优化器状态和激活值**，通常是推理的 **4 倍以上**

这就解释了 7B 模型推理只要 15GB，全参训练却要 80GB 的原因。

## 2.2 逐项拆解（专业定义 + 通俗解释）

### ① 模型权重（Model Weights）

- **专业**：模型所有可学习参数（Linear 层权重、Embedding、LayerNorm 参数等）的存储。
- **通俗**：模型学到的"知识本体"，不管你干什么它都得先装进显存。
- **公式**：

```
显存_权重 (GB) = 参数量(B) × 每参数字节数

FP16/BF16: 参数量(B) × 2
INT8:      参数量(B) × 1
INT4:      参数量(B) × 0.5
```

例：Qwen2.5-7B FP16 → 7 × 2 = **14GB**；INT4 量化 → 7 × 0.5 = **3.5GB**。

### ② 梯度（Gradients）

- **专业**：反向传播计算得到的损失对每个可训练参数的偏导数，与可训练参数**一一对应**。
- **通俗**：老师批改作业时给每个知识点写的"该往哪改"的批注。有多少参数要改，就有多少条批注。
- **关键**：梯度只对**可训练参数**产生。这是 LoRA 省显存的根本原因——LoRA 冻结了 99% 的参数，只有那 0.5% 有梯度。
- **公式**：

```
显存_梯度 (GB) = 可训练参数量(B) × 2   （BF16 梯度）
```

### ③ 优化器状态（Optimizer States）—— 最容易被忽略的显存大户

- **专业**：Adam/AdamW 优化器为每个可训练参数维护一阶动量 m 和二阶动量 v，混合精度训练下通常还额外保存一份 FP32 主权重（master weights）。
- **通俗**：Adam 不是"看一眼批注就改"，它还记着"这个知识点最近几次都往哪边改的"（动量 m）和"这个知识点改动幅度一般多大"（方差 v），外加一本"高精度誊抄本"（FP32 主权重）防止半精度累积误差。三本账，每本都和参数一样大。
- **公式（AdamW 混合精度，最常见配置）**：

```
FP32 主权重: 参数量 × 4
一阶动量 m : 参数量 × 4
二阶动量 v : 参数量 × 4
────────────────────────
显存_优化器 (GB) = 可训练参数量(B) × 12
```

**这就是那个著名的经验法则**：

> **全参微调 ≈ 参数量 × 16 GB**
> 拆解：权重 2 + 梯度 2 + 优化器 12 = **16 Byte/参数**

例：7B 全参微调 = 7 × 16 = **112GB** → 单卡 A100 80G **装不下**，必须上多卡或 ZeRO 切分。

**优化器换一换，显存差很多：**

| 优化器 | 每参数额外字节 | 全参训练总系数 | 说明 |
| --- | --- | --- | --- |
| AdamW（FP32 状态） | 12 | **×16** | 默认，最稳，最费 |
| AdamW（BF16 状态） | 4 | ×8 | 精度略降，省一半 |
| **8-bit AdamW**（bitsandbytes） | 2 | ×6 | 常用省显存手段 |
| SGD + Momentum | 4 | ×8 | 大模型效果一般不如 Adam |
| **Adafactor** | ≈0（分解存储） | ×4~5 | 显存极省，收敛稍慢 |

### ④ 激活值（Activations）

- **专业**：前向传播过程中每一层产生的中间张量，因反向传播需要用它们计算梯度而必须缓存。大小与 batch_size × 序列长度 × 隐藏维度 × 层数成正比。
- **通俗**：算题时的草稿纸。你不能算完就扔——反向求导时还得回头看草稿才知道怎么改。**批次越大、句子越长，草稿纸摊得越开**。
- **关键特性**：这是**唯一一项和参数量无关、和输入数据规模有关**的显存。它也是最容易爆显存的一项，也是最容易优化的一项（梯度检查点）。
- **估算公式（Transformer 单层，BF16）**：

```
显存_激活/层 ≈ batch × seq_len × hidden × (约 10~34 倍系数) × 2 Byte
总激活 ≈ 上式 × 层数
```

系数区间大是因为它取决于实现细节（是否用 FlashAttention、是否融合算子）。**教学与工程中用下面的简化式更实用**：

```
【实用估算】开启 FlashAttention + BF16 时：
显存_激活 (GB) ≈ batch × seq_len × hidden × 层数 × 2 × 12 / 10^9
```

例：7B 模型（hidden=4096, layers=32），batch=1, seq_len=2048：
激活 ≈ 1 × 2048 × 4096 × 32 × 2 × 12 / 10⁹ ≈ **6.4GB**

若 batch 提到 8 → **51GB**，直接爆卡。**这就是为什么调 batch size 是训练时最先动的旋钮。**

**梯度检查点（Gradient Checkpointing / 激活重计算）**：
- **专业**：只保存每个 Transformer Block 边界处的激活，块内激活在反向传播时重新前向计算一遍。
- **通俗**：草稿纸不全留，只留每章的小结；要用中间步骤时现场重算一遍。**省显存，费时间。**
- **效果**：激活显存降至约 √层数 量级，**通常省 60%~80%**，训练时间增加约 **20%~30%**。工程上几乎是标配。

### ⑤ 框架与碎片开销（Overhead）

- **专业**：CUDA Context、cuBLAS/cuDNN 工作区、NCCL 通信缓冲区、PyTorch 缓存分配器产生的显存碎片。
- **通俗**：房子的公摊面积和物业费，不住人但确实占地方。
- **估算**：单卡预留 **1~2GB**；多卡分布式训练 NCCL buffer 再加 **1~2GB**。
- **实践提示**：碎片严重时报 "CUDA OOM but xx GB reserved"，可设 `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True` 缓解。

# 第三章 推理显存计算

## 3.1 推理显存总公式

```
┌──────────────────────────────────────────────────────────┐
│  推理显存 = 模型权重 + KV Cache + 激活(小) + 框架开销         │
│                                                          │
│  显存_推理 (GB) = P × B_w  +  KV_Cache  +  1~2GB          │
│                                                          │
│  P    = 参数量（单位 B，十亿）                              │
│  B_w  = 每参数字节（FP16=2, INT8=1, INT4=0.5）             │
└──────────────────────────────────────────────────────────┘
```

推理时**没有梯度、没有优化器状态**，前向激活算完即弃（只留当前层），所以激活可忽略不计。真正的变量是 **KV Cache**。

## 3.2 KV Cache：推理显存的第二大头

### 它是什么

- **专业**：自回归解码时，为避免对已生成 token 重复计算 Attention 的 Key/Value 矩阵，将每层每个 token 的 K、V 张量缓存下来复用。
- **通俗**：模型生成第 100 个字时，需要"回顾"前 99 个字。如果每次都把前面全部重算一遍，成本是平方级增长的。KV Cache 就是把前 99 个字的"理解结果"记在小本子上，生成新字时直接查本子。**用显存换速度**，这是所有推理框架的核心优化。

### 精确公式

```
┌────────────────────────────────────────────────────────────────┐
│ KV_Cache (Byte) = 2 × L × S × H_kv × D_head × B_kv × N_batch    │
│                                                                │
│  2       = K 和 V 两份                                          │
│  L       = 层数 (num_hidden_layers)                             │
│  S       = 序列总长度 = 输入 prompt + 已生成 token               │
│  H_kv    = KV 头数 (num_key_value_heads)  ← 注意不是注意力头数!   │
│  D_head  = 每个头的维度 = hidden_size / num_attention_heads      │
│  B_kv    = KV 精度字节 (FP16=2, FP8=1, INT8=1)                  │
│  N_batch = 并发请求数                                           │
└────────────────────────────────────────────────────────────────┘
```

**MHA 模型的简化写法**（当 KV 头数 = 注意力头数时，H_kv × D_head = hidden_size）：

```
KV_Cache (Byte) = 2 × L × S × hidden_size × 2
                = 4 × L × S × hidden_size        （FP16）
```

### 为什么必须查 `num_key_value_heads`

现代模型几乎都用 **GQA（分组查询注意力）**：多个 Query 头共享一组 KV 头，专门为了砍 KV Cache。

- **通俗**：本来 32 个人各记一本笔记，现在改成每 4 个人共用一本，笔记本数量从 32 降到 8，**KV Cache 直接省 4 倍**。

以 Qwen2.5-7B 为例（`config.json` 真实值）：

| 参数 | 值 |
| --- | --- |
| num_hidden_layers | 28 |
| hidden_size | 3584 |
| num_attention_heads | 28 |
| **num_key_value_heads** | **4** ← GQA，7 个 Q 头共享 1 组 KV |
| head_dim | 3584 / 28 = 128 |

**算一遍（单请求，序列长度 2048，FP16）：**

```
KV = 2 × 28 × 2048 × 4 × 128 × 2
   = 117,440,512 Byte
   ≈ 0.117 GB  ≈ 120 MB
```

如果它没用 GQA（KV 头 = 28）：`2 × 28 × 2048 × 28 × 128 × 2 ≈ 0.82 GB`，**是 7 倍**。这就是 GQA 的价值。

**记住三条 KV Cache 的规律：**
1. KV Cache 与**序列长度线性增长**——长文本场景（32K、128K）它会超过模型权重本身。
2. KV Cache 与**并发数线性增长**——这是决定 QPS 上限的硬约束。
3. KV Cache 与**参数量无关**，只与层数、hidden、KV 头数有关。

### 并发上限公式（面试高频，能算出来就是加分项）

```
可用于 KV 的显存 = 总显存 × gpu_memory_utilization − 权重显存 − 框架开销
最大并发数 N ≈ 可用于 KV 的显存 ÷ 单请求 KV Cache
```

**完整例题**：A100 80G 部署 Qwen2.5-7B FP16，平均上下文 2048 token，vLLM 的 `gpu_memory_utilization=0.9`，能支持多少并发？

```
可用显存    = 80 × 0.9 = 72 GB
减模型权重  = 72 − 15.2（7.6B 实际参数 × 2）= 56.8 GB
减框架开销  = 56.8 − 2 = 54.8 GB
单请求 KV   = 0.117 GB
最大并发    = 54.8 / 0.117 ≈ 468 条
```

结论：7B 在 A100 上**显存根本不是瓶颈**，瓶颈在算力和带宽——所以实测 QPS 是 20~80，而不是 468。**这个"理论并发远大于实测 QPS"的结论，说明推理性能是算力受限而非显存受限，是很好的面试论点。**

反过来看 72B FP16 双卡：权重 144GB 占满 160GB 中的 90%，剩给 KV 的只有约 10GB，并发能力被显存卡死——**大模型的瓶颈才在显存**。

> **表格使用提醒**：以上是"权重 + 少量 KV"的下限。生产部署要留出并发的 KV 空间，**建议按权重的 1.2~1.5 倍来规划显存**。
> MoE 模型（如 DeepSeek-V3、Qwen3-30B-A3B）的坑：**显存要按总参数量算（全部专家都得装进显存），算力按激活参数量算**。Qwen3-30B-A3B 显存要按 30B 准备（60GB），但推理速度接近 3B。这是面试极易答错的点。

## 3.4 长上下文场景：KV Cache 反超权重

用 Qwen2.5-7B 演示 KV Cache 随上下文的增长（单请求，FP16）：

| 上下文长度 | KV Cache | 占比（相对 15GB 权重） |
| --- | --- | --- |
| 2K | 0.12GB | 0.8% |
| 8K | 0.47GB | 3% |
| 32K | 1.9GB | 13% |
| 128K | **7.5GB** | **50%** |

单请求还好，**但 32K 上下文 × 20 并发 = 38GB KV**，已经超过模型权重。长文本 RAG 服务的显存规划必须把 KV 算进去。

**优化手段：**

| 手段 | 原理（通俗） | 效果 |
| --- | --- | --- |
| **PagedAttention**（vLLM 核心） | 像操作系统管内存那样分页管 KV，不再为每条请求预留最长长度 | 显存浪费从 60%+ 降到 <4% |
| **GQA / MQA** | 多个 Q 头共享 KV 头 | KV 降 4~8 倍 |
| **KV Cache 量化**（FP8/INT8） | KV 也用低精度存 | KV 减半，精度损失极小 |
| **Prefix Caching** | 相同的系统提示词只算一次，多请求共享 | 省显存 + 降首字延迟 |
| **MLA**（DeepSeek） | 把 KV 压缩成低秩潜向量再存 | KV 降至 1/10 量级 |

# 第四章 训练显存计算

## 4.1 全参微调（Full Fine-tuning）总公式

```
┌──────────────────────────────────────────────────────────────────┐
│  显存_训练 = 权重 + 梯度 + 优化器状态 + 激活值 + 框架开销             │
│                                                                  │
│  = P×2  +  P×2  +  P×12  +  Act  +  Overhead                     │
│  = P×16 (GB)  +  Act  +  1~2GB                                   │
│                                                                  │
│  P = 参数量（单位 B）；AdamW + BF16 混合精度                        │
└──────────────────────────────────────────────────────────────────┘
```

**16 这个系数怎么记（通俗版）**：
- 一份**本体**（权重 BF16，2）
- 一份**批注**（梯度 BF16，2）
- 三本**账本**（FP32 主权重 4 + 动量 m 4 + 方差 v 4 = 12）
- 合计 **2+2+12 = 16 Byte/参数**

**例题 1：7B 全参微调，batch=1，seq=2048，开梯度检查点，需要多少显存？**

```
权重      = 7 × 2  = 14 GB
梯度      = 7 × 2  = 14 GB
优化器    = 7 × 12 = 84 GB
────────────────────────
静态小计            112 GB
激活(开检查点)    ≈   2 GB
框架开销          ≈   2 GB
════════════════════════
合计              ≈ 116 GB
```

**结论**：单卡 A100 80G **跑不了** 7B 全参微调。必须用：**2 张卡 + DeepSpeed ZeRO-2**，或 **1 张卡 + ZeRO-Offload（把优化器状态放 CPU 内存）**。

> **教学提醒**：原教材里"7B 全量微调 60~80GB（A100 80G×1）"这个数字是**开了优化器降精度或 offload 的乐观值**。按标准 AdamW FP32 状态算，7B 全参需要 110GB+。上课时要讲清这个差异来自优化器配置，否则学生按 80GB 去实操会 OOM。

**例题 2：为什么 batch size 加大就爆显存？**

7B 模型，seq=2048，**不开**梯度检查点：

| batch size | 激活显存 | 加上 112GB 静态 | 结果 |
| --- | --- | --- | --- |
| 1 | ~6.4GB | 118GB | 2 卡勉强 |
| 4 | ~26GB | 138GB | 2 卡 OOM |
| 8 | ~51GB | 163GB | 需 3 卡 |

静态部分（112GB）不随 batch 变，**激活部分线性增长**。这是训练调参最直观的显存杠杆。

## 4.2 LoRA 微调公式

### LoRA 原理（通俗讲透）

- **专业**：对预训练权重矩阵 W ∈ R^(d×k) 的更新量做低秩分解 ΔW = B·A，其中 A ∈ R^(r×k)、B ∈ R^(d×r)，r ≪ min(d,k)。训练时冻结 W，只更新 A、B。前向为 h = Wx + (α/r)·BAx。
- **通俗**：一本 1000 页的教科书（原模型），你要针对某个考试补充知识。全参微调 = 把整本书重写一遍；LoRA = **在书边上贴便利贴**，只写 5 页便利贴，读的时候书 + 便利贴一起看。书本身没动（冻结），你只需要保管那 5 页便利贴的批注和账本。

**LoRA 可训练参数量公式**：

```
LoRA 参数量 = Σ(每个被适配的层) r × (d_in + d_out)

常见配置：r=8~64，作用在 q_proj/k_proj/v_proj/o_proj（+ MLP 的 gate/up/down）
经验值：可训练参数占总参数的 0.1% ~ 2%
```

例：7B 模型，r=16，只适配 attention 的 4 个投影矩阵 → 可训练参数约 **20M（0.28%）**；若加上 MLP 层 → 约 **40M（0.57%）**。

### LoRA 显存公式

```
┌────────────────────────────────────────────────────────────────┐
│  显存_LoRA = P×2（冻结权重，仍需全量装载）                        │
│            + P_lora×2   （梯度，只有 LoRA 参数有）               │
│            + P_lora×12  （优化器状态，只有 LoRA 参数有）          │
│            + 激活值      （★ 与全参微调基本相同，不省！）          │
│            + 1~2GB                                             │
└────────────────────────────────────────────────────────────────┘
```

**这是本讲最重要的认知纠偏：LoRA 省的是"梯度 + 优化器状态"，不省"权重"，也基本不省"激活值"。**

- **通俗**：便利贴方案让你不用抄书、不用给整本书记账，但**书还是得整本摆在桌上**（权重要全装载），**做题的草稿纸还是照样铺开**（激活值照旧，因为前向仍要过所有层）。

**例题 3：7B LoRA 微调（r=16，40M 可训练参数），batch=4，seq=2048，开梯度检查点**

```
冻结权重       = 7 × 2      = 14   GB
LoRA 梯度      = 0.04 × 2   = 0.08 GB
LoRA 优化器    = 0.04 × 12  = 0.48 GB
激活(开检查点) ≈             4    GB
框架开销       ≈             2    GB
═══════════════════════════════════
合计           ≈            20.6 GB   → 单张 4090 24G 可跑 ✓
```

**对比**：全参 116GB vs LoRA 20.6GB，**省了 82%**。省下来的几乎全部来自优化器状态（84GB → 0.48GB）。

### QLoRA：再省一半

- **专业**：将基座模型量化为 4-bit NF4 存储，前向时按需反量化为 BF16 计算，配合 Double Quantization 与 Paged Optimizer。
- **通俗**：连书本身都印成"缩印版"（4bit），要读某页时临时放大。**桌子更小也放得下，代价是每次读要花一点放大时间。**

```
显存_QLoRA ≈ P×0.5 + P_lora×14 + 激活 + 1~2GB
```

7B QLoRA：`3.5 + 0.56 + 4 + 2 ≈ 10GB` → **单张 3060 12G 就能微调 7B**。代价：训练速度比 LoRA 慢约 **30%~50%**（反量化开销）。

## 4.3 全参 / LoRA / QLoRA 显存对照表

假设：batch=1，seq=2048，AdamW，BF16 混合精度，开梯度检查点

| 模型规模 | 全参微调 | LoRA(r=16) | QLoRA(4bit) | 全参最低配置 | LoRA 最低配置 |
| --- | --- | --- | --- | --- | --- |
| 0.5B | ~10GB | ~3GB | ~2GB | 1×4090 | 任意 8G 卡 |
| 1.5B | ~28GB | ~6GB | ~3GB | 1×A100 40G | 1×3060 12G |
| 7B / 8B | **~116GB** | **~18GB** | **~10GB** | 2×A100 80G | **1×4090 24G** |
| 14B | ~230GB | ~34GB | ~16GB | 4×A100 80G | 1×A100 40G |
| 32B | ~520GB | ~72GB | ~30GB | 8×A100 80G | 1×A100 80G |
| 70B / 72B | ~1.15TB | ~150GB | **~48GB** | 16×A100（2 机） | 2×A100 80G |
| 110B | ~1.8TB | ~230GB | ~70GB | 不推荐 | 4×A100 80G |

> **原教材对照**：原表格"13B LoRA 需 80G（1 张 A100）"偏保守，那是**不开梯度检查点 + batch 较大**时的真实占用；按本表配置 13B LoRA 约 32GB。**上课要强调：显存数字必须绑定 batch size、seq_len、是否开检查点这三个前提，否则无法比较。**

## 4.4 分布式训练：显存怎么被切开

当单卡装不下，就要把那五个"房客"分到多张卡上。

### DeepSpeed ZeRO 三个阶段（通俗版）

| 阶段 | 切什么 | 通俗比喻 | 7B 单卡显存 | 通信开销 |
| --- | --- | --- | --- | --- |
| ZeRO-0（DDP） | 什么都不切，每卡一份完整副本 | 8 个人各买一整套书和账本 | 116GB | 最低 |
| **ZeRO-1** | 切优化器状态 | 账本分开保管，用时互相问 | ~44GB（8卡） | 低 |
| **ZeRO-2** | 切优化器 + 梯度 | 账本和批注都分开 | ~30GB（8卡） | 中 |
| **ZeRO-3** | 切优化器 + 梯度 + **权重** | 连书都撕开分着拿，读到哪页现借 | ~16GB（8卡） | **高** |
| ZeRO-Offload | 把优化器状态挪到 CPU 内存 | 账本搬到隔壁房间 | ~30GB（单卡） | 受 PCIe 限制，慢 |

**ZeRO-N 阶段显存公式（N 张卡）**：

```
ZeRO-1: P×2 + P×2 + P×12/N + Act
ZeRO-2: P×2 + (P×2 + P×12)/N + Act
ZeRO-3: (P×2 + P×2 + P×12)/N + Act    ← 即 P×16/N + Act
```

**选择建议（工程实践）**：
- 显存够 → 用 **ZeRO-2**，性价比最高（省得多，通信不重）
- 显存不够 → 上 **ZeRO-3**，但要有 NVLink，否则 PCIe 通信会让训练慢 2 倍以上
- 只有一张卡且必须全参 → **ZeRO-Offload**，慢但能跑

### 并行方式对比

| 并行方式 | 切分维度 | 通俗解释 | 适用场景 |
| --- | --- | --- | --- |
| **数据并行 DP/DDP** | 切数据 | 每人一套完整书，各做不同的题，最后汇总答案 | 模型能装进单卡 |
| **张量并行 TP** | 切单层矩阵 | 一道大矩阵乘法，几个人各算一部分列 | 单层都装不下；**必须 NVLink**，一般 TP ≤ 8（不跨机） |
| **流水线并行 PP** | 切层 | 32 层分给 4 个人，每人 8 层，像流水线传递 | 跨机训练；注意 bubble 空转 |
| **序列并行 SP** | 切序列长度 | 长句子切段，每人处理一段 | 长上下文训练（32K+） |
| **专家并行 EP** | 切 MoE 专家 | 不同专家放不同卡 | MoE 模型 |

**大规模训练常见组合**：`TP=8（机内） × PP=4（跨机） × DP=N`，业界叫 **3D 并行**。

# 第五章 算力（FLOPs）与训练时间估算

显存决定**能不能跑**，算力决定**跑多久**。这一章解决"训练要几个小时"这个必被追问的问题。

## 5.1 训练算力总公式

```
┌────────────────────────────────────────────────────────┐
│         训练总算力 C ≈ 6 × P × D  (FLOPs)               │
│                                                        │
│  P = 参数量（个数，不是 B）                              │
│  D = 训练 token 总数                                    │
│  6 = 前向 2 + 反向 4（反向的计算量约为前向的 2 倍）        │
└────────────────────────────────────────────────────────┘
```

**为什么是 6？（通俗）**
- 前向：每个参数对每个 token 做 1 次乘 + 1 次加 = **2 FLOPs**
- 反向：既要算「对输入的梯度」又要算「对权重的梯度」，是前向的 2 倍 = **4 FLOPs**
- 合计 **6 FLOPs / 参数 / token**

开了梯度检查点要多一次前向重算，系数变成 **8**。

**推理算力**：只有前向，`C ≈ 2 × P × D`。

## 5.2 训练时间公式

```
┌──────────────────────────────────────────────────────────────┐
│  训练时间(秒) = (6 × P × D) ÷ (GPU数 × 单卡峰值算力 × MFU)      │
│                                                              │
│  MFU (Model FLOPs Utilization) = 有效算力利用率                │
│    单卡/机内 NVLink: 0.4 ~ 0.55                               │
│    多机分布式:       0.3 ~ 0.45                               │
│    LoRA 微调:        0.3 ~ 0.4（反向计算少但仍要过全部层）       │
└──────────────────────────────────────────────────────────────┘
```

**MFU 通俗解释**：显卡标称 312 TFLOPS 是"实验室最理想状态"，实际训练要等数据、要通信、要读写显存，真正用在算上的只有 **40% 左右**。就像标称百公里加速 3 秒的车，市区通勤平均时速只有 30 公里。**面试时能说出 MFU 这个词并给出 0.4 的经验值，专业度立刻上一档。**

## 5.3 完整例题（课堂重点，务必手算一遍）

### 例题 A：7B 模型 LoRA 微调 3000 条数据，单卡 A100，要多久？

**第一步：算 token 总数**

```
假设每条样本平均 1000 token，训练 3 个 epoch
D = 3000 条 × 1000 token × 3 epoch = 9 × 10^6 token
```

**第二步：算总算力**

```
P = 7 × 10^9
C = 6 × 7×10^9 × 9×10^6 = 3.78 × 10^17 FLOPs
```

> 注意：LoRA 虽然只更新 0.5% 参数，但**前向和反向传播仍要穿过全部参数**，所以计算量不能按 LoRA 参数量算，仍按全参数量估。LoRA 省的是显存和优化器计算，不是主干计算量。

**第三步：算时间**

```
A100 FP16 = 312 × 10^12 FLOPS，取 MFU = 0.35（LoRA）
有效算力 = 312×10^12 × 0.35 = 1.09 × 10^14 FLOPS

时间 = 3.78×10^17 / 1.09×10^14 = 3467 秒 ≈ 0.96 小时
```

**结论：约 1 小时**。与原教材"7B 生成式任务 LoRA 1~4 小时"吻合——上下浮动来自样本长度、是否开检查点、数据加载效率。

### 例题 B：13B 全参微调 5000 条，2×A100，要多久？

```
D = 5000 × 1000 × 3 = 1.5 × 10^7 token
C = 6 × 13×10^9 × 1.5×10^7 = 1.17 × 10^18 FLOPs
有效算力 = 2 × 312×10^12 × 0.45 = 2.81 × 10^14 FLOPS
时间 = 1.17×10^18 / 2.81×10^14 = 4164 秒 ≈ 1.16 小时
```

**咦，怎么比原教材"10~30 小时"快这么多？** 这是必须给学生讲清的一课：**理论算力时间是下限**。实际训练时间还要叠加：
- 梯度检查点重计算：**× 1.3**
- ZeRO-2/3 通信等待：**× 1.5 ~ 2**
- 数据加载、tokenize、checkpoint 保存：**× 1.2**
- 多轮实验、调参、失败重跑：**× 2 ~ 5**

`1.16 × 1.3 × 1.8 × 1.2 ≈ 3.3 小时`（单次成功训练），再算上调参迭代就到了十几小时量级。**所以面试报时间要报"实测值"，不要报理论值。**

## 5.4 训练时间与数据量参考表（扩充版）

| 模型规模 | 任务类型 | 推荐数据量 | LoRA 时间（A100 80G） | 全参时间（A100 80G） | 备注 |
| --- | --- | --- | --- | --- | --- |
| 0.5B~1.5B | 分类 | 每类 300~500 条 | 10~30 分钟（单卡） | 20~60 分钟（单卡） | 小模型优先全参 |
| **7B** | 分类（SFT） | 每类 500 条 | 0.5~1 小时（单卡） | 1~3 小时（需 2 卡） | |
| **7B** | 生成式（SFT） | 1,000~3,000 条 | 1~4 小时（单卡） | 4~12 小时（2 卡） | |
| 7B | DPO 偏好对齐 | 2,000~5,000 对 | 3~8 小时（单卡） | — | 显存约为 SFT 的 2 倍（需参考模型） |
| **13B/14B** | 分类（SFT） | 每类 ≤1,000 条 | 1~3 小时（单卡） | 4~10 小时（需 2 卡） | |

**两条铁律（面试必说）：**

> **1. 数据质量 > 数据数量。高质量 1,000 条往往优于低质量 10,000 条。**
> **2. 灾难性遗忘防线：全参微调数据量不要超过 15,000 条**，且学习率要压到 1e-5 量级；超过这个规模建议改用 LoRA + 混入 5%~10% 通用数据（replay）来保住通用能力。

**LoRA vs 全参的工程结论**：LoRA 训练时间缩短 **50%~70%**，显存节省 **60%~85%**，效果损失通常在 **1%~3%** 以内（任务越接近预训练分布，损失越小；需要注入大量新知识时差距会拉大）。**LoRA 是工程首选，全参是效果兜底。**

## 5.5 RL 训练的显存特殊性（进阶）

面试问到 RLHF/PPO 时，要点在于**同时有 4 个模型在显存里**：

| 模型 | 作用（通俗） | 是否训练 | 显存 |
| --- | --- | --- | --- |
| Actor | 正在学的学生 | ✓ | P×16 |
| Critic | 打分的助教 | ✓ | P×16 |
| Reward Model | 出题的考官 | ✗ | P×2 |
| Reference | 原版学生（防跑偏） | ✗ | P×2 |

```
PPO 显存 ≈ P×16 × 2 + P×2 × 2 = P×36  （!!）
```

7B PPO 全参 ≈ 250GB+，**这就是"14B RL 任务需要一整台 8 卡 A100"的原因**。
现在主流做 **GRPO**（DeepSeek 提出）可以**去掉 Critic**，显存降到 P×20 左右，是显著优化。

# 第六章 模型选型与并发

## 6.1 按任务类型选型

选型的第一原则：**先看任务是判别式还是生成式**，不要一上来就用大模型。

| 任务类型 | 推荐模型（举例） | 参数量级 | 理由 |
| --- | --- | --- | --- |
| 文本分类 / NER / 意图识别 | BERT / RoBERTa / MacBERT / ERNIE | 110M~340M | **Encoder-only**，双向注意力适合理解任务，推理快（毫秒级），显存小 |
| 文本生成 / 对话 / 摘要 | Qwen2.5 / Qwen3 / GLM-4 / LLaMA3.1 | 7B~72B | **Decoder-only**，自回归生成能力强 |
| 向量检索（Embedding） | BGE-M3 / Qwen3-Embedding / text-embedding-3 | 0.6B~8B | 专为语义检索优化，输出定长向量 |
| 重排序（Rerank） | BGE-Reranker-v2 / bce-reranker | 300M~600M | **Cross-Encoder**，Query 与 Doc 拼接后交互打分，精度高于向量检索 |
| 多模态（图文） | Qwen2.5-VL / InternVL / GLM-4V | 2B~72B | 视觉编码器 + LLM，支持 OCR、图表理解 |
| 语音识别 | Whisper / SenseVoice / Paraformer | 0.2B~1.5B | 专用 ASR 架构 |
| 代码生成 | Qwen2.5-Coder / DeepSeek-Coder | 7B~33B | 代码语料专项训练 |

### 一条硬性纪律：严禁给 BERT 设计 LoRA 微调

**为什么（要能讲透原因，不能只背结论）：**

1. **技术上可行，但工程上没有意义**。LoRA 存在的唯一理由是"全参微调显存装不下"。BERT-base 只有 110M 参数，全参微调显存 = 110M × 16 = **1.76GB**，一张最便宜的卡都能跑，**没有任何显存压力需要解决**。
2. **小模型用 LoRA 会掉点**。BERT 参数少、表达能力本就有限，再用低秩约束限制它的更新空间，效果反而不如全参。大模型有冗余，低秩更新够用；小模型没有这份冗余。
3. **增加部署复杂度**。LoRA 需要额外管理 adapter 权重和合并逻辑，对一个 1.76GB 的训练任务来说完全是负收益。

**面试话术**：
> LoRA 的适用前提是"全参微调显存不够"。BERT 只有 110M~340M，全参微调不到 2GB 显存，成本极低，没有必要引入低秩约束。而且小模型本身表达能力有限，低秩更新会限制它的拟合能力，效果通常不如全参。LoRA 主要解决的是 7B 以上模型全参微调显存爆掉的问题。

## 6.3 并发与吞吐

### 三个必须分清的性能指标

| 指标 | 全称 | 通俗解释 | 典型目标 |
| --- | --- | --- | --- |
| **TTFT** | Time To First Token | 从提问到吐出第一个字的等待时间（受 prefill 算力影响） | < 1s（对话）；< 300ms（实时） |
| **TPOT** | Time Per Output Token | 每个后续字的间隔（受**显存带宽**影响） | < 50ms（约 20 字/秒，比人阅读快） |
| **QPS / 吞吐** | Queries Per Second | 每秒能处理完多少请求 | 按业务量算 |

**通俗解释三者关系**：TTFT 是"服务员多久来点单"，TPOT 是"菜上得快不快"，QPS 是"这家店一小时能接待多少客人"。**优化方向常常冲突**：加大 batch 能提高 QPS，但会拉长单个请求的 TTFT。

### 并发参考表（vLLM 部署，A100 80G）

| 模型 | 精度 | 显卡 | QPS 参考 | 单请求生成速度 | 说明 |
| --- | --- | --- | --- | --- | --- |
| Qwen2.5-7B | FP16 | 1×A100 | **20 ~ 80** | 40~60 tok/s | 短输入短输出取上限 |
| Qwen2.5-7B | INT4(AWQ) | 1×4090 | 10 ~ 30 | 30~50 tok/s | 性价比部署 |
| Qwen2.5-14B | FP16 | 1×A100 | **30 ~ 50** | 30~45 tok/s | |
| Qwen3-30B-A3B | FP16 | 1×A100 | 25 ~ 50 | 40~60 tok/s | MoE，显存吃 60G 但速度快 |
| Qwen2.5-32B | FP16 | 1×A100 | **5 ~ 15** | 15~25 tok/s | KV 空间被权重挤压 |
| Qwen2.5-72B | INT4 | 1×A100 | **~3** | 8~15 tok/s | 显存极限，并发很低 |
| Qwen2.5-72B | FP16 | 2×A100 | **5 ~ 12** | 15~20 tok/s | TP=2 |
| DeepSeek-V3 | INT8 | 4×A100 | 8 ~ 20 | 20~30 tok/s | MoE 优势 |

> **必须加的免责说明**：QPS 强依赖于**输入长度、输出长度、并发模式、vLLM 版本**。同一个 7B 模型，「100 字输入 + 50 字输出」和「4000 字输入 + 1000 字输出」的 QPS 能差 10 倍以上。**面试报 QPS 一定要同时说明测试条件**，否则会被认为没做过真实压测。

### 提升吞吐的手段（按性价比排序）

1. **换 vLLM/SGLang**（如果还在用 transformers 裸跑）→ 吞吐提升 **5~20 倍**，这是最大的一步
2. **开启 Continuous Batching**（vLLM 默认开）→ 让请求随到随进，不等凑满一批
3. **量化到 INT8/AWQ-INT4** → 权重减半到 1/4，腾出的显存全部给 KV Cache，并发提升明显
4. **Prefix Caching** → 系统提示词长的场景（RAG）TTFT 直降 50%+
5. **调 `gpu_memory_utilization`** → 从默认 0.9 提到 0.95，多榨出几 GB 给 KV（风险：容易 OOM）
6. **张量并行 TP** → 加卡，注意必须有 NVLink
7. **投机解码（Speculative Decoding）** → 小模型先猜、大模型验证，单请求速度提升 1.5~2 倍
8. **多实例 + 负载均衡** → 单卡装得下时，2 张卡跑 2 个独立实例通常比 TP=2 一个实例吞吐更高

## 6.4 按部署资源选型速查

- **显存 ≤ 24GB（1×4090 / L4）**：7B FP16（推荐）或 14B INT4；32B INT4 极限可跑但 KV 空间紧张、并发差
- **显存 40GB（1×A100 40G / L20 48G）**：14B FP16 或 32B INT4
- **显存 80GB（1×A100 80G）**：32B FP16（推荐）/ 30B-A3B / 72B INT4（并发仅个位数）
- **显存 160GB（2×A100 80G）**：72B FP16 / 110B INT4
- **对延迟敏感**：小模型 + 量化 + 投机解码，优先压 TTFT
- **对效果敏感**：大模型 + FP16，接受低并发，或用 MoE 兼顾
- **对成本敏感**：MoE 模型（Qwen3-30B-A3B）或 INT4 量化

## 7.1 一页纸公式总表（建议打印）

```
═══════════════════ 显 存 公 式 ═══════════════════

【基准记忆】FP16 下，1B 参数 = 2GB 显存

【推理】
  显存 = P×2 + KV_Cache + 1~2GB              (FP16)
  显存 = P×0.5 + KV_Cache + 1~2GB            (INT4)

  KV_Cache(Byte) = 2 × 层数 × 序列长度 × KV头数 × head_dim × 2 × 并发数
  最大并发 ≈ (总显存×0.9 − 权重 − 2GB) ÷ 单请求KV

【训练 · 全参】
  显存 = P×2(权重) + P×2(梯度) + P×12(AdamW) + 激活 + 2GB
       = P×16 + 激活 + 2GB

【训练 · LoRA】
  显存 = P×2 + P_lora×14 + 激活 + 2GB
       ≈ P×2 + 激活 + 2GB       (LoRA 部分可忽略)

【训练 · QLoRA】
  显存 = P×0.5 + P_lora×14 + 激活 + 2GB

【激活值】
  激活 ≈ batch × seq_len × hidden × 层数 × 24 / 10^9  GB
  开梯度检查点 → 降 60%~80%，时间 +20%~30%

【ZeRO 切分（N 卡）】
  ZeRO-1: P×2 + P×2 + P×12/N + 激活
  ZeRO-2: P×2 + P×14/N + 激活
  ZeRO-3: P×16/N + 激活

═══════════════════ 算 力 公 式 ═══════════════════

【训练算力】 C = 6 × 参数量 × token总数      (开检查点用 8)
【推理算力】 C = 2 × 参数量 × token总数

【训练时间】 T(秒) = 6×P×D ÷ (卡数 × 单卡TFLOPS × MFU)
             MFU: 单机 0.4~0.55 / 多机 0.3~0.45 / LoRA 0.3~0.4
             理论时间 × 2~3 = 工程实际时间

【生成速度上限】 tok/s ≈ 显存带宽(GB/s) ÷ 模型权重(GB)

═══════════════════ 关 键 系 数 ═══════════════════

  精度：FP32=4  FP16/BF16=2  FP8/INT8=1  INT4=0.5  (Byte/参数)
  全参训练总系数：AdamW-FP32=16  AdamW-BF16=8  8bit-Adam=6  Adafactor=4~5
  PPO 全参：P×36    GRPO：P×20
```

## 7.2 显存不够时的处置清单（按"先试哪个"排序）

| 顺序 | 手段 | 省显存幅度 | 副作用 |
| --- | --- | --- | --- |
| 1 | 降 batch size（配合梯度累积保持等效批量） | 线性 | 几乎无（吞吐略降） |
| 2 | 开梯度检查点 | 激活降 60~80% | 时间 +20~30% |
| 3 | 缩短 max_seq_len | 线性（激活/KV） | 长样本被截断 |
| 4 | 全参 → LoRA | 总体降 70~85% | 效果损失 1~3% |
| 5 | 换 8-bit AdamW / Adafactor | 优化器降 50~80% | 收敛略慢 |
| 6 | LoRA → QLoRA（4bit 基座） | 再降 50% | 速度 −30~50% |
| 7 | 上 DeepSpeed ZeRO-2 / ZeRO-3 | 按卡数线性 | 通信开销，需 NVLink |
| 8 | ZeRO-Offload（优化器搬 CPU） | 优化器全免 | 慢 2~3 倍 |
| 9 | 加卡 / 换大显存卡 | — | 花钱 |

**推理侧显存不够**：① 量化到 INT8/INT4 → ② 降 `max_model_len` → ③ 降并发 → ④ KV Cache 量化 → ⑤ 张量并行加卡。

## 7.3 课堂练习（含答案）

### 练习 1（基础）
Qwen2.5-14B-Instruct 用 FP16 推理部署，单卡 A100 40G 够吗？

<details>
<summary>答案</summary>

权重 = 14 × 2 = 28GB；框架开销 2GB；剩 40 − 30 = 10GB 给 KV Cache。
单请求 2K 上下文 KV 约 0.2GB，理论可支持 ~50 并发。
**结论：够用，但没有余量。** 生产建议 A100 80G 或 INT8 量化到 14GB 后部署在 40G 卡上。
</details>

### 练习 2（推理·KV Cache）
某模型 40 层，hidden=5120，注意力头 40，KV 头 8。部署时要支持 **32K 上下文 × 16 并发**，KV Cache 需要多少显存（FP16）？

<details>
<summary>答案</summary>

```
head_dim = 5120 / 40 = 128
单请求 = 2 × 40 × 32768 × 8 × 128 × 2 = 5.37 × 10^9 Byte ≈ 5.37 GB
16 并发 = 5.37 × 16 ≈ 86 GB
```
**结论：仅 KV Cache 就要 86GB，超过一张 A100 80G。** 必须用 KV 量化（INT8 → 43GB）或降并发/降上下文，或多卡部署。这就是长上下文服务的真实痛点。
</details>

### 练习 3（训练）
要在 **2×A100 80G** 上全参微调 Qwen2.5-7B，batch=2，seq=2048。直接跑会 OOM 吗？怎么配置？

<details>
<summary>答案</summary>

朴素 DDP：每卡都要完整的 112GB 静态显存 → **必然 OOM**（单卡只有 80G）。

可行配置：**DeepSpeed ZeRO-2 + 梯度检查点**
```
权重      = 14 GB（每卡完整）
梯度+优化器 = (14 + 84) / 2 = 49 GB
激活(检查点) ≈ 3 GB
开销       ≈ 2 GB
──────────────────────
每卡合计    ≈ 68 GB  ✓ 可跑（余量偏紧）
```
若仍紧张：改 ZeRO-3（每卡 = 112/2 + 激活 ≈ 59GB），或换 8-bit AdamW。
</details>

### 练习 4（训练时间）
7B 模型，10,000 条数据，平均 800 token，训练 2 epoch，LoRA，单卡 A100。估算训练时间。

<details>
<summary>答案</summary>

```
D = 10000 × 800 × 2 = 1.6 × 10^7 token
C = 6 × 7×10^9 × 1.6×10^7 = 6.72 × 10^17 FLOPs
有效算力 = 312×10^12 × 0.35 = 1.09 × 10^14
T = 6.72×10^17 / 1.09×10^14 = 6165 秒 ≈ 1.7 小时（理论）
工程实际 ≈ 1.7 × 2 ≈ 3.5 小时
```
另外提示：全参微调 10,000 条已接近灾难性遗忘的 15,000 条警戒线，这个规模更适合 LoRA。
</details>

### 练习 5（综合选型）
业务需求：法律合同问答，要求私有化部署、回答准确率高、日均 5,000 次查询（峰值 10 QPS）、上下文需 8K。预算 1 台 8 卡 A100 80G 服务器。请给出方案。

<details>
<summary>答案要点</summary>

**方案：4 卡推理 + 2 卡训练 + 2 卡备用/Embedding**

1. **主模型**：Qwen2.5-32B-Instruct FP16，TP=2 部署 2 个实例（共 4 卡）
   - 单实例显存：64GB 权重 + KV 空间，8K 上下文单请求 KV ≈ 1GB
   - 2 实例负载均衡后 QPS 可达 10~30，满足峰值
2. **RAG 组件**：BGE-M3 Embedding + BGE-Reranker-v2（1 卡足够，可与主模型共卡）
3. **微调**：法律领域数据 3,000~5,000 条做 LoRA（2 卡，约 5 小时）
4. **上下文优化**：开 Prefix Caching（法律问答系统提示词长），TTFT 可降一半
5. **为什么不选 72B**：72B FP16 要 2 卡且 QPS 仅 5~12，8K 上下文下 KV 空间更紧；32B 在效果与并发间是更好的平衡点。若准确率实测不达标，再升级到 72B INT4。
</details>

## 7.4 面试高频追问速答

| 问题 | 一句话答法 |
| --- | --- |
| 7B 模型推理要多少显存？ | FP16 约 15GB，INT4 约 4.5GB，加 KV Cache 和开销，单卡 4090 24G 够跑。 |
| 为什么全参微调是推理的 8 倍？ | 推理只要权重（P×2），训练还要梯度（P×2）和 AdamW 优化器状态（P×12），合计 P×16。 |
| LoRA 到底省了什么？ | 省梯度和优化器状态（占全参显存的 87%），**不省权重、基本不省激活值**。 |
| KV Cache 怎么算？ | 2×层数×序列长×KV头数×head_dim×精度字节×并发。注意用 `num_key_value_heads`，GQA 能省 4~8 倍。 |
| 并发上限怎么估？ | （总显存×0.9 − 权重 − 开销）÷ 单请求 KV Cache。 |
| 训练要多久？ | 时间 = 6×参数量×token数 ÷（卡数×算力×MFU），MFU 取 0.4，理论值再乘 2~3 倍是实际值。 |
| MoE 模型显存怎么算？ | **显存按总参数算**（所有专家都要装载），**算力/速度按激活参数算**。 |
| A100 和 A800 差别？ | 单卡算力显存完全相同，仅 NVLink 互联带宽从 600 降到 400 GB/s，只影响多卡分布式效率。 |
| 显存够了为什么还是慢？ | decode 阶段是显存带宽受限，生成速度上限 ≈ 带宽 ÷ 权重大小，不是算力问题。 |
| 用什么优化器省显存？ | 8-bit AdamW（P×6）或 Adafactor（P×4~5），代价是收敛略慢。 |
