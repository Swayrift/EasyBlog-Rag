让 Agent 跑得久，难点往往不在模型会不会做，而在它还记不记得自己做到哪了。上下文压缩就是处理这件事的工程手段——但它的流行说法（"窗口快满了就清一清"）严重低估了它。压缩是有损压缩，丢错了东西，Agent 不会报错，只会开始重复劳动、甚至绕过你设过的限制。

## 一、为什么要压缩

一次推理塞进上下文的东西，大致五类：系统指令、工具定义、对话历史、工具输出，以及被读进来的代码和文件内容。它们争的是同一个预算——模型的上下文窗口。

限制来自两个层面。

**资源层面**：token 越多，单次前向的计算量、显存、延迟和成本同步上升。而且这笔钱是每轮重复付的，第 N 轮要重新为前面 N-1 轮买单。

**能力层面**（更要紧）：上下文越长，模型对其中任意一段的注意力越稀薄。Lost in the Middle 发现长输入的首尾召回明显好于中段；Chroma 在 18 个模型上的 context rot 评测显示，即使是很简单的任务，性能也会随输入变长而退化。社区把这段区间叫"变笨区"（dumb zone）。

所以压缩的动机不只是"装不下"，更是"装太多会变笨"。经验判断很直接：**一个更小、组织得更好的上下文，通常比一个更大、更嘈杂的上下文表现更好。** 下面所有技巧都从这句话推出来。

## 二、先立标准：什么该留，什么该丢

压缩是有损压缩，所以得先写出它的损失函数：

> **丢掉这条信息，会让下一轮决策发生改变吗？**

不会改变，就丢。会改变，就必须留——而且不该指望摘要帮你留。按这个标准，上下文里的信息大致分四档：

| 档位 | 内容 | 处理 |
| --- | --- | --- |
| 决策与理由 | 选了什么、否了什么、为什么 | 必须留 |
| 未完成的承诺 | "还要回来改 X"、待办、下一步 | 必须留 |
| 环境与状态 | 分支名、工作目录、已改的文件、任务 ID、权限范围 | 必须留，且要精确 |
| 原始工具输出 | 文件全文、搜索结果、测试日志、diff | 优先丢，已消化过的几乎全是死 token |

第一档里要特别点出**被否掉的路径**：价值最高、token 最便宜，却最容易被摘要丢掉。因为在叙述里，"我们试过 X，失败了"读起来像一段弯路，而不像一个结论。代价是 Agent 花四十分钟重新走进同一个死胡同，而整个过程没有任何报错。

## 三、如何压缩上下文

常见说法是两条路：删除不重要的信息、记录重要的信息。这个分法作为起点没问题，但漏掉了两个同样重要的手段。完整的分类是四个字：**弃、缩、写、隔。**

| 手段 | 代表实现 | 主要代价 |
| --- | --- | --- |
| 弃 | 滑动窗口、工具结果清除、观察遮蔽 | 容易丢约束和任务定义 |
| 缩 | compaction 摘要、分层摘要 | 摘要失真、内容位置重排 |
| 写 | 交接文档、结构化笔记、memory tool、按需取回 | 要工程投入，且模型可能忘了去读 |
| 隔 | 子代理 | 子代理看不到全局，可能返工 |

### 1. 弃：直接丢弃

- **滑动窗口**：丢掉最早的若干轮。实现最简单，但它丢掉的常常正是任务定义和约束，所以适合闲聊，不适合长任务。
- **工具结果清除**：把已经消化过的工具调用结果替换成一行占位文本，保留"这次调用发生过"的记录。Anthropic 把它做成了平台能力（`clear_tool_uses_20250919`）：默认在输入超过 100K token 时触发，保留最近 3 组工具调用/结果；`clear_at_least` 用来保证一次清够多少 token（不够就不动手，避免白破缓存）；`exclude_tools` 设白名单；`clear_tool_inputs` 决定是否连调用参数一起清。
- **思考块清除**：开启扩展思考后，thinking block 也占大块空间，`clear_thinking_20251015` 用来控制保留多少。
- **观察遮蔽（observation masking）**：JetBrains 2025 年的研究思路——把工具输出换成一行摘要，但完整保留推理链。因为推理链里往往已经含有工具输出的信息，而且更紧凑。这能砍掉一半以上 token，性能几乎不掉。

### 2. 缩：摘要替换

这就是通常说的 compaction：把较早的历史交给模型生成摘要，用摘要替换原文，只保留最近若干轮完整对话。

关键在摘要模板，不在摘要质量。让模型"写一份好总结"，它会保住故事线、丢掉结论。更该让它输出结构化字段：目标 / 已定决策与理由 / 被否方案及原因 / 未完成承诺 / 环境状态（分支、目录、改动文件）/ 下一步。这不是文风偏好，是字段设计——**字段在，信息才有地方落。**

空间还是紧张就做分层：先出一份详细摘要，不够再压成要点，再不够压成骨架，逐层用保真度换空间。

### 3. 写：外置到窗口之外

"记录重要的信息"这一路，本质是把状态搬出窗口：

- **交接文档**：一个阶段跑完让模型写一份交接文档，下一段开始前先读它。
- **结构化笔记**：模型自己维护 NOTES.md、待办清单这类文件。Anthropic 的 memory tool 就是把这个模式做成了标准工具。
- **按需取回（just-in-time retrieval）**：上下文里只放"路径"，真需要时再去读全文。
- **原文不删、可检索**：压缩不等于销毁，原始上下文留在磁盘上，让 Agent 需要时自己捞回来。

这一路的优势是可靠——写在外面的东西不会被摘要顺手丢掉。

### 4. 隔：子代理隔离

让子代理在自己的干净窗口里做深度探索，只把结论交回主代理，通常 1000–2000 token。主代理永远看不到那 20 次工具调用。

Anthropic 的多代理研究架构用了这个模式：子代理可以消耗几万 token 去探索，回来只给一段浓缩结论，在内部研究评测上相对单代理提升了 90.2%。LangChain 的 Deep Agents、Google ADK 也都把子代理当一等公民。

它还带出一条多代理系统的设计原则：**共享记忆靠通信，不靠共享内存。** 交接时该传的是压缩后的结论，不是把父窗口整个倒过去。

## 四、什么时机压缩

时机直接决定体验：压太早，细节白丢；压太晚，来不及。

**阈值触发**（最主流）：占用到一个比例就自动压缩。Claude Code 文档化的实现里，自动压缩缓冲区曾从 45K 降到 33K——约 200K 窗口的 16.5%，也就是占用约 83.5% 时触发；现在可以通过 `/autocompact`、启动参数或环境变量把窗口配到 100K–1M 区间。经验上触发点放 **75%–80%** 比较合适：生成摘要本身要占 token，拖到 99% 才压，只剩最粗暴的压缩可做，丢的东西最多。

**任务边界触发**：一个子任务收尾、阶段切换时主动压一次。语义上这是最自然的切点。

**手动触发**：`/compact`，而且可以带指令指定关注点，比如 `/compact 保留决策和未决问题`。

**事件触发**：工具返回超大输出、hook 在特定生命周期点介入等。

还有一个容易被忽略的结构性问题：压缩通常发生在轮次之间，而单轮内部的工具调用可以把窗口从 170K 撑到 400K。触发点不能只看轮次开始时的占用，得给单轮内的膨胀留余量。

## 五、压缩会坏在哪里

这部分最贵，也最少被写进架构图。

**约束失忆——最危险的一种。** 压缩系统是为"任务连续性"优化的：保目标、保当前状态、保下一步。而用户随口说的一句约束——"改任何东西之前先问我"、"不要往这张表写生产数据"——在摘要器眼里既不是任务也不是状态，属于最早被丢的东西。宾州州立大学的研究（COMPINT）量化了这一点：注入的会话级约束平均只有 **17%** 能活过压缩；未压缩时合规率在 59%–71%，压缩后多数方案掉到接近"从未说过这条约束"的水平；即便专门写提示词要求保留约束，留存率仍不到 40%。这不是质量问题，是安全问题：一个以为自己没被限制过的 Agent，会去做它本不该做的事。

**压缩抖动（thrash）。** 压缩后第一个动作就是重新读那个大文件，窗口立刻又满，再压一次。每压一轮掉一点保真度，连着几轮就把信息磨平了。

**重复劳动与死循环重试。** 摘要保住了目标（"更新这五个文件"），丢掉了完成记录，于是 Agent 重读读过的文件、重跑跑过的变换——更糟的是把不该重复的操作做了两遍。同理，一次失败尝试的因果链丢掉后，它会再次撞上同一堵墙。有评测给过具体差距：代码类任务上，压缩后的上下文让 Agent 只得 4.0/10，上下文完整时是 6.0/10，差距几乎全部来自重复读取和重复失败。

**位置变了，注意力也变了。** 压缩会把原本"最新、最显眼"的内容推到窗口中段，而模型对中段召回最差。信息名义上还在，实际上取不到。

**摘要自身会失真。** 摘要器是第二个模型，有它自己的目标函数，默认目标常常是"写一份像样的总结"，而不是"让接下来 200 轮不出错"。

**成本与延迟没被计入。** 每次压缩都是一次额外的模型调用，要读完这段历史的全部。用户侧看到的是对话中途莫名卡一下；账单上是一笔没人认领的开销。

**缓存失效。** 清除内容会使 prompt cache 的前缀失效。`clear_at_least` 存在的意义正是这个：一次清得不够多，破缓存的代价不划算。

## 六、怎么做稳：一份操作清单

1. **关键状态外置，每轮重注入，不进摘要。** 安全规则、权限范围、未完成承诺，放在压缩不经过的通道里。
2. **压缩后重新加载，而不是指望摘要保住。** Claude Code 的做法是压缩后从磁盘重读 CLAUDE.md——身份和规则指令必须完整存活，任何摘要都可能丢掉关键措辞。同类做法还有压缩后触发的 hook，用来把被压掉的状态重新注入。
3. **用结构化摘要模板**：决策（含被否）/ 承诺 / 状态 / 下一步。
4. **保留最近 N 轮原文**，让手头正在做的事不缺细节。
5. **压缩而非销毁。** 原始上下文留在磁盘上，允许检索。
6. **从源头减小工具输出**：分页、用 grep 而不是整文件读、给输出设上限。治源头比事后压缩便宜得多。
7. **做对抗性回归测试。** 在长会话早期埋一条约束（比如"永远不要写 prod-orders 表"），把会话跑过压缩阈值，再问一个会触发违规的问题，看它是否仍然遵守。每类约束（安全规则 / 凭据范围 / 未完成承诺）都该有一条这样的用例，并在模型或压缩实现换代后重跑。

## 七、一句话

压缩不是"清垃圾"，是**有损压缩**。做这件事的目的不是腾地方，而是找到那组最小的高信号 token——足够让下一步做对，一个也不多。

上下文窗口不是记忆系统，是计算面。任何需要活得比一轮更久的东西，都该住在窗口外面。
