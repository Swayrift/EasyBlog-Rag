RAG 系统的评估，目前主流的指标采用来自 RAGAS 提出的那一套。RAGAS 里的指标不少，常用的有 4 个，分别是：Faithfulness（忠实性）、Answer Relevancy（答案相关性）、Context Precision（上下文精确率）、Context Recall（上下文召回率）。

把这四个名字放在一起看，会发现它们的分工很清楚：**Context 开头的两个测检索，另外两个测生成。** 检索是上限，生成是下限，分开测才能定位问题。

## Faithfulness

忠实度得分衡量的是"答案有没有超出给定资料的范围"，也就是模型有没有在编。测量步骤如下：

1. 让 LLM 把答案拆成独立声明
2. 逐条对比检索文档，看文档是否支持该条独立声明
3. 得分 = 被支持的声明数 / 总声明数

这个指标打的是幻觉。需要注意两点：它只看答案和**检索结果**的关系，不看检索结果本身对不对——如果检索回来的资料本身就是错的，模型照着说，忠实度依然是满分。另外，它不关心答案对不对题，只关心答案有没有出处。

## Answer Relevancy

答案相关性得分衡量的是"答案有没有答到点上"，算法是反着来的：不去判断问题和答案像不像，而是拿答案去反推问题，再看反推出来的问题跟原问题像不像。测量步骤如下：

1. LLM 根据答案生成 N 个提问（RAGAS 默认 N 取 3）
2. 计算原问题与 LLM 猜的提问的余弦相似度
3. 得分 = 平均相似度

这么设计有它的道理：直接比问题和答案的相似度会偏袒"复读问题"的回答，而"由答案反推问题"能同时惩罚答非所问和答得不完整。

但也要清楚它的盲区——**它完全不管答案对不对**。一个自信地把错答案说得头头是道、逻辑自洽的回答，在这个指标上可以拿满分。所以它必须和 Faithfulness 一起看。

## Context Precision

上下文精确率得分衡量的是"检索回来的内容里，有多少是真的用得上"。测量步骤如下：

1. LLM 挑出文档中对回答有用的句子
2. 得分 = 有用的句子数 / 文档总句数

需要注意的是，RAGAS 的实现比"有用句子占比"更讲究一点：它是**带位置权重的**。同样一个有用的片段，排在第一位和排在第十位，贡献不一样，排得越靠前权重越高。因为模型的注意力对长上下文的开头和结尾最好，中间那段最容易被忽略，检索排序本身就是答案质量的一部分。

这个指标低，说明检索回来的东西噪音多；但低不等于"漏了"，漏没漏是下一个指标的事。

## Context Recall

上下文召回率得分衡量的是"该找到的东西，有没有都找回来"。测量步骤如下：

1. 把标准答案拆成若干条独立声明
2. 逐条检查能否在检索到的上下文里找到支撑
3. 得分 = 能被支撑的声明数 / 标准答案总声明数

它和 Context Precision 是一对：精确率看"捞回来的有多少有用的"，召回率看"有用的有多少被捞回来了"。只优化其中一个通常没用——把 Top-K 调大能提升召回率，但精确率会掉，最后还是会拖累答案质量。

**它是四个指标里唯一必须有人工标注的标准答案（ground truth）才能算的。** 前三个都可以只靠问题、答案、检索结果算出来，召回率不行——因为"该找到什么"只有人知道。

## 四个指标放在一起看

| 指标 | 测的是 | 需要标准答案 | 主要抓什么问题 |
| --- | --- | --- | --- |
| Faithfulness | 生成 | 否 | 幻觉、无中生有 |
| Answer Relevancy | 生成 | 否 | 答非所问、答不完整 |
| Context Precision | 检索 | 否 | 检索噪音多、排序差 |
| Context Recall | 检索 | 是 | 该给的资料没给 |

值得说明的是，这四个只是最常用的一组。RAGAS 里还有 Answer Correctness（和标准答案比对，兼顾事实与语义）、Answer Semantic Similarity、Noisy Context Recall 等；如果系统里有"该拒答就得拒答"的需求，还得单独测拒答的准确率。指标是按你要回答的问题挑的，不是越多越好。

## 用 LLM 给 LLM 打分，靠谱吗？

先说结论：能用，但只能当"相对比较的仪器"，不能当"绝对真值"。

上面四个指标的算法里，几乎每一步都要靠 LLM 判断——拆声明、判断有没有被支撑、挑有用的句子。裁判本身会带来误差，而且这些误差是系统性的，不是随机噪声：

1. **位置偏见**：把两个待评对象换个顺序，结论可能就变了。
2. **长度偏见**：更长的答案、更长的上下文更容易被判成"更完整"，哪怕多出来的都是废话。
3. **自我偏好**：裁判偏爱自己家族的输出。用某一家模型当裁判，去评另一家模型的输出，分数会系统性偏低。
4. **提示词敏感**：打分提示词改一个措辞，整体分数能挪动一大截。
5. **分数不可比**：换了裁判模型、甚至只是升级了版本，历史分数就失效了——你没法拿今天的 0.82 跟三个月前的 0.85 比。

研究里常被引用的一条数据是：GPT-4 当裁判时与人类判断的一致率在 80% 上下（来自 MT-Bench 那项工作）。80% 听起来还行，但放在"要不要上线"的语境里意味着：每五个判断就有一个跟人不一致，而你不知道是哪五个。

所以更实际的态度是**把它当成一个需要校准的仪器**：在同一套裁判配置下比较 A 方案和 B 方案，是可信的；拿它的绝对分数去对外宣称"我们的准确率是 0.87"，是不可信的。

## 三种缓解方案

1. **工程手段：把偏见用工程方式抵掉。** 同一组样本正反各评一次再取平均，抵消位置偏见；用与生成模型不同家族的模型当裁判，减少自我偏好；多个裁判独立打分（或同一裁判多次采样）后取多数或中位数，把方差压下去；最后，裁判模型版本、提示词、采样参数全部固定并版本化，换版本就重新建立基线。这几个手段成本都不高，通常是第一步就该做的。

2. **微调小模型：把裁判从"通用大模型"换成"专用小模型"。** ARES 是这条路上的代表，它用少量合成数据训练一个轻量裁判模型（DeBERTa 这类判别式模型）来打上下文相关性、忠实性和答案相关性。好处很直接：判别式模型的单样本评估成本极低、速度快、可复现——同一个输入永远给同一个分，不会因为你手抖把 temperature 调成 0.7 就换一个结果。它还额外用一小份人工标注数据做预测驱动推断（PPI），让评估结果带上置信区间，而不是一个孤零零的数字。代价是换模型、换领域、换语言时裁判可能要重训。

3. **人机混合：自动跑全量，人工只审关键样本。** 全量样本走自动评估，成本才可控；低分样本和高风险场景（涉及金额、医疗、法律、对外发布）交人工复核；再保留一份人工标注的小集合专门用来校准——它的主要作用不是给系统打分，而是告诉你"自动分数和人判断之间的偏差有多大"。这也是唯一能回答"这套评估到底能不能信"的办法。

## 实际工程中怎么做评估？

分三层跑，让问题可以被定位，而不是只知道"效果不太好"。

**第一层：单独测检索。** 只用检索指标（Context Recall、Context Precision、Hit Rate、MRR、NDCG@k），不跑生成。优点是快、便宜、稳定——同一份数据跑两遍结果完全一样，所以在调 chunk 大小、embedding 模型、Top-K、混合检索权重这些参数时，这一层最适合做快速对比。检索就是整个系统的上限：正确资料没被捞出来，后面怎么生成都是错的。

**第二层：单独测生成。** 把正确的上下文直接喂给模型（而不是检索结果），只评估生成质量：Faithfulness、Answer Relevancy，加上与标准答案的一致性。这样能把"检索没找对"和"模型没用对"两种失败区分开——这两种情况在端到端指标里长得一模一样，光看端到端你永远查不出来。

**第三层：端到端测试。** 从用户问题进、最终答案出，整条链路跑一遍。这一层最接近真实体验，但出了问题最难定位，所以它是"验收"层，不是"调试"层。

三层都离不开一份人工标注的黄金测试集。约 50 条是个够用的起点，关键不在数量，而在覆盖得全：

- 常见的简单问题，保证基本盘
- 需要跨文档、多跳才能回答的问题
- 含专有名词、型号、编号、精确数值的问题
- 表述模糊、本身有歧义的问题
- **知识库里根本没有答案的问题**——看系统会不会老实地讲"没找到"，而不是硬编一个。这一类往往最能暴露问题
- 容易踩坑的边界输入

每条样本至少要带上：问题、标准答案、以及正确的那几段资料（算 Context Recall 要用）。

最后用诊断矩阵检查问题出在哪一层：

| 端到端 | 检索 | 生成 | 结论 |
| --- | --- | --- | --- |
| 差 | 好 | 好 | 交互问题 |
| 差 | 差 | 好 | 检索问题 |
| 差 | 好 | 差 | 生成问题 |
| 差 | 差 | 差 | 全都得调 |
| 好 | 差 | 好 | 测试集太简单 |

- **差 / 好 / 好 → 交互问题**：检索没问题，生成也没问题，但拼起来是错的，说明问题出在中间那一层。查提示词模板、上下文拼接与截断、块的排列顺序（中间位置最容易被忽略），以及多轮对话里的问题改写。
- **差 / 差 / 好 → 检索问题**：资料压根没捞回来。回去调切块方式、embedding 模型、Top-K，或者加上混合检索与重排。
- **差 / 好 / 差 → 生成问题**：资料已经送到嘴边了，模型没用上。查提示词有没有明确要求"只根据给定资料回答"、上下文是不是被截断了、模型是不是在凭记忆编。
- **差 / 差 / 差 → 全都得调**：别同时改，先把第一层做对，再做第二层。
- **好 / 差 / 好 → 测试集太简单**：端到端好、检索指标却差，通常不是系统有什么绝活，而是你的测试问题太容易，检索随便捞几段也够模型蒙对。这时的正确动作是补难样本，不是庆祝。

## 几条经验

1. **先建评估集，再动手调系统。** 没有基线的优化，等于没有优化。
2. **分数只跟自己的上一版比。** 不同实现、不同裁判、不同数据集之间的分数不可比，跨项目比分数是没有意义的。
3. **50 条样本上的 0.01～0.02 差异是噪声。** 看趋势，别看小数点。
4. **把评估配置一起版本化。** 数据集版本、裁判模型、提示词、检索参数都要记。否则你没法解释上周那个提升到底是从哪来的。
5. **评估集要防污染。** 别让测试问题的答案躺在知识库里，被检索出来送到模型面前——那不是评估，那是开卷考试。
6. **真实用户反馈是最终裁判。** 点踩率、追问率、人工抽检，这些才是终审。自动指标只是它的代理。
