RAG 的本质是检索增强生成：先从外部资料里检索出相关内容，再把它交给大模型作为回答依据。这样模型不必"记住"全部知识，也能回答训练数据里没有的、或者刚刚才更新的东西。

但很多人对 RAG 有一个默认印象：RAG 一定要以向量的形式存储。实际上并不是这样。检索的关键从来不是"向量"，而是"用合适的数据结构，回答合适的问题"。常见的 RAG 系统有三种，分别使用向量数据库、关系型数据库和图数据库的存储方式。

## 对于非结构化数据

如果是非结构化的数据（文章、PDF、聊天记录这类没有固定字段的文本），我们使用向量数据库来存储。流程如下：文档读取 -> 文档切块 -> 向量化存储 -> 向量检索。这几步各自都有讲究：

- **文档读取**：把 PDF、Word、HTML 解析成纯文本。这一步的质量决定了整条链路的上限——解析错了，后面再讲究也救不回来。
- **文档切块**：按固定长度切，并让相邻块之间留一些重叠，避免一个完整句子被切断在边界上；再好一点的做法是按标题层级或语义切。切得太大，召回的内容里噪音多；切得太小，模型拿到手又缺上下文。
- **向量化存储**：用 embedding 模型把每个块转成向量，连同元数据（来源、页码、标题）一起存进向量库。索引和查询必须用同一个模型，否则向量空间对不上；元数据也别丢，检索时可以先用它做过滤，再算相似度。
- **向量检索**：把用户问题也转成向量，算相似度取出 Top-K，通常还会再加一步重排（rerank）来提升精度。

这套流程有一个天生的弱点：它匹配的是"语义相近"，不是"事实正确"。碰上专有名词、型号、编号、精确数值，向量检索往往还不如关键词检索。所以实际系统里常见混合检索——向量召回和 BM25 各取一批，再用 RRF 之类的策略融合，效果比单走一路稳定得多。

## 对于结构化数据

如果是结构化数据（订单、库存、用户、指标这类存在表和字段里的数据），我们使用关系型数据库存储数据，使用 SQL 语句检索。

为什么不继续用向量？因为这类问题要的答案是精确的、带条件的、需要聚合的："上个月华东区退款率最高的三个品类"——这里有时间范围、有分组、有排序。向量检索做不了这些，它只能告诉你"哪段文字看起来最像"，而"看起来最像"和"算得对"是两件事。

主流做法是 Text-to-SQL，流程如下：用户提问 -> 生成 SQL -> 数据库执行 -> 模型总结结果。

这条路上有几个必须注意的点。表结构（DDL）和字段注释要给全，否则模型不知道字段叫什么、是什么意思；数据库账号只给只读权限；生成的 SQL 要先校验再执行，并限制单次扫描行数和执行时间，免得一句写错就把库拖垮。做得好，这类问题会答得很准；做得糙，它会一本正经地给你一个错的数字——而且比答不出来更危险。

## 对于图数据

如果是图数据，我们使用图数据库存储数据，使用 Cypher/SPARQL 语句检索。流程如下：用户提问 -> 生成 Cypher/SPARQL -> 图数据库执行 -> 模型总结结果。

图数据库适合的是"关系本身就是答案"的问题。比如"这家公司的供应商里，有哪些同时也在给它最大的竞争对手供货"——答案不在任何一篇文档里，而藏在实体之间的多条连线上。这类多跳查询用向量检索基本无解，用 SQL 要写一串自连接，用图数据库就是一句 Cypher：

```cypher
MATCH (c:Company {name: "A"})-[:SUPPLIES]->(s:Supplier)-[:SUPPLIES]->(rival:Company)
RETURN s.name, rival.name
```

和 Text-to-SQL 一样，这里也是让模型根据图谱里已有的节点类型和关系类型来生成查询语句，执行后拿到结果再交给模型组织回答。

图还有一个别的方案给不了的好处：可解释。检索结果是具体的路径，你能看见"它是怎么推出来的"，而不只是一个相似度分数。

顺带一提，GraphRAG 这类做法是把图用在更上层——先在图上做社区划分和摘要，再回答那些需要跨文档归纳的问题（比如"这批资料整体在讨论什么"）。它解决的是全局性问题，和上面的关系查询不是一回事。

## 三种方式怎么选

| 数据形态 | 存储 | 检索方式 | 擅长的问题 |
| --- | --- | --- | --- |
| 非结构化文本 | 向量数据库 | 向量相似度（常配关键词混合检索、重排） | 找相关资料、语义相近的内容 |
| 结构化数据 | 关系型数据库 | SQL | 精确条件、聚合、排序、统计 |
| 图数据 | 图数据库 | Cypher / SPARQL | 多跳关系、路径推理、可解释的推导 |

需要说明的是，这三者不是三选一。一个成熟的 RAG 系统往往是多路的：先用一个轻量的路由判断问题该走哪条路，需要时并行走多条、再把结果融合。用户问"上季度退款率怎么样"，路由就该把它交给 SQL，而不是让它去向量库里捞几段看起来相关的文字。

## 小结

RAG 的重点不在"向量"，而在"检索"。向量只是处理非结构化文本最顺手的一种手段，不是唯一手段。真正的判断标准是：这个问题的答案，天然长在哪种数据结构里？答案在文本里就用向量，在字段里就用 SQL，在关系里就用图。

这个问题想清楚了，RAG 的效果上限就已经定下来一半。
